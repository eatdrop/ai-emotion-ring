# 产品负责人工作规范 / Product Owner Workflow

## 中文

### 核心职责

产品负责人持续回答五个问题：目标用户是谁、真实场景是什么、最重要的问题是什么、为什么现在要做、怎样证明产生价值。

### 工作流程

1. 通过访谈、观察、问卷或真实使用记录收集证据。
2. 将问题写成可验证的需求，不直接跳到功能方案。
3. 在 PRD 中定义目标、非目标、用户流程、优先级、指标和验收标准。
4. 与四位技术负责人进行可行性、成本、风险和依赖评审。
5. 拆分为可在一个迭代内验收的 Issue。
6. 开发中管理需求变化，避免口头插单。
7. 联调后按照验收标准验收，不以“看起来差不多”代替证据。
8. 发布后收集指标和反馈，决定继续、调整或停止。

### 优先级原则

优先解决高频、高痛、可验证且符合比赛和长期产品方向的问题。优先级至少考虑用户价值、证据强度、风险、实现成本、依赖和学习价值。

### PRD 最低内容

- 背景和证据
- 目标用户与场景
- 问题定义
- 目标与非目标
- 用户流程
- 功能和非功能需求
- 数据、隐私和合规要求
- 验收标准
- 指标
- 依赖、风险、里程碑和负责人

### 边界

产品负责人不替代技术负责人做架构、模型或固件决策；技术负责人也不能绕过产品负责人改变用户流程、需求范围和验收标准。争议应记录证据、方案和决策人。

## English

### Core responsibilities

The product owner continuously answers five questions: who the target user is, what the real context is, what problem matters most, why it should be solved now, and how value will be demonstrated.

### Workflow

1. Gather evidence through interviews, observation, surveys, or real usage records.
2. Frame a testable problem before jumping to a feature solution.
3. Define goals, non-goals, user flow, priority, metrics, and acceptance criteria in the PRD.
4. Review feasibility, cost, risk, and dependencies with all four technical owners.
5. Break work into Issues that can be accepted within one iteration.
6. Manage requirement changes during development and avoid verbal scope injection.
7. Accept integrated work against explicit criteria rather than “looks close enough.”
8. After release, collect metrics and feedback to continue, adjust, or stop.

### Prioritization

Prioritize frequent, painful, testable problems that fit both the competition and long-term product direction. Consider user value, evidence strength, risk, implementation cost, dependencies, and learning value.

### Minimum PRD contents

- Background and evidence
- Target users and scenarios
- Problem statement
- Goals and non-goals
- User flow
- Functional and non-functional requirements
- Data, privacy, and compliance requirements
- Acceptance criteria
- Metrics
- Dependencies, risks, milestones, and owners

### Boundaries

The product owner does not replace technical owners for architecture, model, or firmware decisions. Technical owners must not bypass the product owner when changing user flows, scope, or acceptance criteria. Disputes must record evidence, options, and the decision owner.
